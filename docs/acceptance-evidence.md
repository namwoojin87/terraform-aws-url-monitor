# 제출용 운영 검증과 장애 시연 증빙

이 문서는 공개 가능한 검증 결과와 앞으로 실행할 절차를 구분한다. 아래 기존 결과의 기준일은 **2026-09-07**이며, 문서 작성 자체가 새로운 AWS 실행이나 검증을 의미하지 않는다. 운영 절차의 공통 기준은 [운영 runbook](runbook.md), 전체 구성은 [아키텍처](architecture.md)를 따른다.

추가 수동 1회 실행과 PR 게시 후 실제 CI 결과는 [마무리 검증 기록](final-verification.md)에 별도 기록했다. 한국시간 15:50:56의 새 표본은 HTTP 200 / UP / 299ms, 현재 상태·이력 저장 일치, Scheduler OFF 유지로 확인했다. 아래 이전 시연 결과와 혼합하지 않는다.

CloudWatch의 Lambda `Duration`은 함수 전체 실행시간이다. 검사기가 기록한 HTTP `response_ms`와 다른 측정값이므로 두 값을 같은 지표나 같은 그래프로 설명하지 않는다. 대시보드를 배포해도 URL Scheduler가 자동으로 활성화되지는 않는다.

### 대시보드 IAM 변경의 실환경 검증

마지막 검증 시각은 UTC `2026-09-07T05:22:33.399618+00:00`이다. 사용자 승인 범위의 bootstrap 관리 정책 `aws_iam_policy.deploy`만 적용하여 **0 added / 1 changed / 0 destroyed**로 완료했다. 기존 문장 9개를 유지하고 `ManageProjectDashboard` Allow 문장에 `cloudwatch:GetDashboard`, `cloudwatch:PutDashboard`, `cloudwatch:DeleteDashboards`만 추가했다. 리소스 범위는 해당 프로젝트 대시보드 하나의 정확한 글로벌 ARN이며 계정 ID를 포함한 원문 ARN은 제출하지 않는다.

적용 후 현재 정책을 직접 읽어 검토한 계획의 정책과 의미상 일치함을 확인했다. 역할의 신뢰 정책과 정책 연결은 그대로였고, 새로 실행한 전체 bootstrap plan은 종료 코드 `0`으로 변경 없음이었다. IAM 시뮬레이션은 적용 전 14개 조합 모두 거부, 적용 후 다음과 같이 목표 3개 허용·범위 밖 11개 거부였다.

| action–resource 조합 | 개수 | 적용 후 시뮬레이션 결과 |
| --- | --- | --- |
| 정확한 프로젝트 대시보드의 Get / Put / Delete | 3 | allowed |
| 같은 계정의 비슷한 이름 대시보드의 Get / Put / Delete | 3 | denied |
| 같은 계정의 무관한 이름 대시보드의 Get / Put / Delete | 3 | denied |
| 합성한 다른 계정 대시보드 ARN의 Get / Put / Delete | 3 | denied |
| `cloudwatch:ListDashboards`, `cloudwatch:PutMetricData`의 `Resource=*` | 2 | denied |

기존의 다른 정책 조건 때문에 시뮬레이터가 요구한 S3 prefix와 `iam:PassedToService`의 대표 컨텍스트를 제공했으며 누락 컨텍스트는 없었다. **이 결과는 시뮬레이션 검증이며 실제 대시보드 생성·조회·삭제 호출의 성공 증빙이 아니다.** Scheduler의 입력·설정은 그대로이고 `DISABLED`, 대시보드는 존재하지 않는 상태였다. 이번 IAM 변경으로 새 GitHub commit/push·CI 실행, 보안 예외 승인·적용, PPT 갱신은 수행하지 않았으며 전체 프로젝트 완료를 의미하지 않는다.

상세 변경 범위와 검증 근거는 [대시보드 IAM 변경 기록](dashboard-iam-change.md)을 참조한다.

## 3. 운영 `demo`를 보존하는 수동 장애 재시연

### 시작 조건과 권한 경계

이 시연은 기존 Lambda를 **최대 5회 순차 수동 호출**하여 전용 lab 대상만 검사한다. 운영 `demo`의 URL, 상태 항목, Scheduler 입력, 스케줄 상태, SNS 구독은 수정하지 않는다. 시작 전 운영 설정이 `https://example.com`, 예상 HTTP `200`, 타임아웃 5초, Scheduler `DISABLED`임을 확인한다.

기존 SNS 구독 수신자에게 정상 전이 경로 기준 시험메일 2건(장애 1건·복구 1건)이 발송되는 실제 작업이다. 진행자는 이미 승인된 시연 범위에 해당 수신자로의 시험 발송이 포함되는지 확인하고, 시연 식별자와 예정된 시험메일 제목을 사전에 공유한다. 수신자·토픽·구독을 새로 만들거나 변경하는 절차는 포함하지 않는다.

수동 실행에는 승인된 비루트 운영자 세션을 사용한다. 필요한 작업은 해당 Lambda의 `InvokeFunction`, 해당 Scheduler의 조회, 두 테이블의 제한된 `GetItem`/`Query`, 필요한 로그·지표 조회이다. GitHub plan 역할이나 Lambda 실행 역할에 시연용 권한을 추가하지 않는다. IAM 정책·배포·삭제가 필요해지면 이 시연과 분리하여 변경 범위를 검토한다.

1. 계정과 리전을 비공개 세션에서 확인한다. 제출 자료에는 계정 ID나 ARN을 복사하지 않는다.
2. 이번 실행 전용 식별자 `lab-incident-<UTC-run-id>`를 정하고 두 테이블에 같은 식별자의 기존 항목이 없는지 제한된 키 조회로 확인한다. 기존 항목이 있으면 재사용·덮어쓰지 말고 새로운 식별자를 정한다.
3. 운영 `demo`의 현재 상태에서 공개 가능한 필드와 Scheduler 상태·정상 설정만 실행 전 기준으로 기록한다. 원본 상태나 전체 이벤트는 공개하지 않는다.
4. 다음 이벤트를 템플릿으로 준비하고, `<UTC-run-id>`를 앞에서 선택한 값으로 바꾼다. `targets`에는 lab 하나만 넣는다.

```json
{
  "failure_threshold": 2,
  "state_ttl_days": 7,
  "history_ttl_days": 7,
  "targets": {
    "lab-incident-<UTC-run-id>": {
      "url": "https://example.com",
      "expected_statuses": [200],
      "timeout_seconds": 5
    }
  }
}
```

첫 호출은 위 정상 설정으로 lab의 초기 `UP`을 만든다. 2~4번째 호출은 **같은 lab 식별자**에서 `expected_statuses`만 `[503]`으로 바꾸고, 5번째 호출에서 `[200]`으로 복원한다. 모든 호출의 URL은 `https://example.com`, 타임아웃은 5초로 유지한다. HTTPS 인증서 검증을 끄거나 `--insecure`/검증 우회 코드를 사용하지 않는다.

이는 정상 HTTP `200` 응답을 일부러 예상 코드 `[503]`과 불일치시키는 **판정 실패 주입 시험**이다. 외부 사이트에 장애를 일으키거나 실제 사이트 장애를 관측하는 시험이 아니며, 사이트가 HTTP `503`을 반환했다고 표현하지 않는다. 주입 구간의 예상 기록은 실제 `status_code=200`, `healthy=false`, `error_category=HTTP_STATUS`이다.

### 실행 순서와 중단 기준

호출은 `RequestResponse` 방식으로 하나씩 완료를 확인한 다음 진행한다. 새 ID의 초기 항목은 없고, 첫 정상 호출을 포함한 다섯 결과의 상태 순서는 `UP → PENDING_DOWN → DOWN → DOWN → UP`이다. 초기 정상, 2회 실패 임계값, 3번째 실패 억제, 정상 판정 복원을 각각 기록한다.

| 수동 호출 | `expected_statuses` | 예상 현재 상태 | 예상 연속 실패 수 | 예상 전이와 알림 |
| --- | --- | --- | --- | --- |
| 1 | `[200]` | `UP` | 0 | 초기 정상, 전이 알림 없음 |
| 2 | `[503]` | `PENDING_DOWN` | 1 | 첫 판정 실패, 전이 알림 없음 |
| 3 | `[503]` | `DOWN` | 2 | `OUTAGE`, 장애 시험메일 1건 |
| 4 | `[503]` | `DOWN` | 3 | 추가 장애 알림 없음 |
| 5 | `[200]` | `UP` | 0 | `RECOVERY`, 복구 시험메일 1건 |

위 표는 절차의 **예상 결과**이다. 실제로 확인한 상태·DB 결과는 아래 별도 표에 기록하며, 위 표의 알림 예상값을 발행·수신 실측값으로 사용하지 않는다. 재시연 시 각 호출 후 다음 항목을 확인한다.

- Lambda Invoke API의 HTTP `200`만으로 URL 판정이 정상이라고 판단하지 않는다. `FunctionError`가 없고 함수 응답이 `checked=1`, `errors=0`인지 확인한다. 의도한 HTTP 코드 판정 실패도 함수는 정상 종료할 수 있다.
- 일관된 읽기(`ConsistentRead`)로 lab의 현재 상태와 방금 `checked_at`에 해당하는 이력 항목을 조회한다. 검사 시각·모니터 상태·응답시간·만료값을 대조한다.
- 각 호출의 UTC 시작·종료 시각 안에 새 `checked_at`이 있고, 시각이 호출마다 달라 총 5개의 이력이 생겼는지 확인한다. 이 시연은 매번 실제 HTTP `200`을 전제로 한다. 2~4번째 이력의 HTTP 코드도 `200`이어야 하며 주입한 예상값 `503`을 실제 응답으로 기록하지 않는다.
- SNS 발행 지표, 토픽 전달 보고, 받은편지함 실수신은 구분한다. 해당 lab ID의 전이 로그와 시연 시간 범위를 대조하여 관측한 수준만 기록한다. 토픽 전체의 합계만으로 특정 이메일의 받은편지함 도착·열람을 단정하지 않는다.
- `FunctionError`, 모호한 호출 응답, 실제 HTTP `200`이 아닌 응답·통신 실패, 예상과 다른 상태, 이력 저장 실패가 발생하면 중단한다. 상태·이력·전이 로그를 먼저 확인하고 자동 재시도하거나 다섯 번을 넘겨 호출하지 않는다. SNS 성공 후 DB 쓰기 실패 같은 상황에서는 중복 알림 가능성이 있어 exactly-once를 주장하지 않는다.

이 절차는 Lambda 검사 로직·DB 쓰기·SNS 전이를 확인하는 **수동 시연**이다. Scheduler의 실행 시점·전달 권한·재시도 경로를 새로 검증하는 절차가 아니며, 자동 URL 검사 활성화도 포함하지 않는다.

### 종료와 정리

이번 실제 시연은 lab 최종 `UP`, 운영 `demo` 변경 없음, Scheduler 설정 변경 없이 `DISABLED` 유지로 종료했다. 리소스는 삭제하지 않았으며 lab 상태·이력은 7일 TTL로 만료되도록 남겼다. 아래 항목은 재시연에도 적용하는 정리 기준이다.

1. 운영 `demo`의 정상 대상 설정과 공개 가능한 현재 상태 필드가 실행 전후 같고 Scheduler가 여전히 `DISABLED`인지 확인한다. 예상하지 못한 차이는 덮어써서 숨기지 말고 기록한다.
2. lab은 다섯 번째 호출 후 `UP`으로 남긴다. lab ID는 Scheduler 입력에 추가하지 않았으므로 후속 예약 호출 대상이 아니다. 중간에 중단했다면 복구 성공으로 표시하지 말고 실제 마지막 상태와 중단 사유를 남긴다.
3. 기본 정리 방법은 lab의 상태·이력 항목이 각각 7일 TTL로 만료되도록 두는 것이다. 실제 삭제는 비동기이며 즉시 삭제를 보장하지 않는다. 로그는 기존 7일 보관 설정을 따른다.
4. 즉시 삭제가 별도로 필요하면 권한 있는 운영자가 이번 lab ID와 정확한 항목 키를 확인한 뒤 해당 항목만 처리한다. 테이블 삭제, 전체 스캔 기반 일괄 삭제, 운영 `demo` 삭제, Lambda 역할에 삭제 권한 추가는 이 절차에 포함하지 않는다.
5. 임시 이벤트·호출 응답 파일은 이번 시연에서 만든 정확한 파일만 확인하여 정리한다. 공유 계정의 다른 파일·원격 상태·기존 배포 계획은 건드리지 않는다.
